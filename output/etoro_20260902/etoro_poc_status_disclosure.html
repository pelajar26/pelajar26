eToro Internal Infrastructure Disclosure
via Unauthenticated API Status Endpoints

Program eToro — Bugcrowd
Reporter komeng rooket
Scope *.etoro.com
Services Affected 3 Microservices (Systemic)
Discovered 2026-09-02
Auth Required None

Three production eToro microservices expose diagnostic health-check endpoints that return sensitive internal infrastructure data without any authentication. Any unauthenticated HTTP client can enumerate Kubernetes pod IPs, pod names, deployed git commits, .NET runtime versions, and Azure Kubernetes cluster regions for three distinct services — including the KYC Proxy, which sits in front of eToro's identity verification pipeline.

This is a systemic misconfiguration across eToro's ASP.NET Core microservices platform, where the diagnostic status middleware is bound on public ingress routes without authentication or IP allowlisting, as opposed to the internal Kubernetes liveness/readiness probe network where it belongs.

⚠ Elevated Risk — KYC Identity Pipeline

The KYCProxy application sits between eToro's partner portal and the third-party identity verification provider. This service processes government-issued documents, passport/ID scans, and biometric data for regulatory KYC compliance. Exposing this service's internal pod IP (10.204.73.117) and Helm chart version (v1.217.0) on an unauthenticated endpoint is the most sensitive instance of this systemic issue.

Attack Scenarios
⊕ SSRF Amplification
Disclosed pod IPs (10.203.85.110, 10.204.83.206, 10.204.73.117) provide concrete SSRF pivot targets if any other eToro endpoint accepts user-controlled URLs — no guessing of internal address ranges needed.
⊕ Version Exploitation
Exact .NET versions (8.0.7, 8.0.3, 10.2.8) and application versions enable targeted CVE research against the specific runtime and framework versions deployed in production.
⊕ Git Correlation
Full git commit hashes from three services, correlated with any source code leaks, GitHub Actions logs, or developer repos, can map deployed code to source history — revealing unpatched commits.
⊕ Topology Mapping
Pod naming convention (aff-api-f-*, client-logs-api-*, kycproxy-*) reveals Kubernetes deployment names, enabling inference of additional undiscovered services by pattern extrapolation.
Remediation
  • 1
    Restrict status routes to internal Kubernetes probe network only. Apply a Kubernetes NetworkPolicy or NGINX ingress annotation so only the kubelet's probe address range can reach /api/status and /api/v1/status. No public ingress route should expose these paths. ingress.kubernetes.io/whitelist-source-range: "10.0.0.0/8"
  • 2
    Sanitize the status response on any externally-facing health endpoint. If an external load-balancer probe genuinely requires an HTTP 200, return only {"status":"healthy"} — strip machineName, machineIp, commit, branch, infraVersion, and chartVersion entirely.
  • 3
    Add authentication middleware to diagnostic routes. If the diagnostic endpoints must remain public-facing for operational monitoring, protect them with an internal service token or mTLS.
  • 4
    Audit all other eToro microservices using the same ASP.NET Core middleware pattern for the same unauthenticated status endpoint exposure. The naming convention of the affected services suggests a shared service template or base class — fix it in the template, not service-by-service.
